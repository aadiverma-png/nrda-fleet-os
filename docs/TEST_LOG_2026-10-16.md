## Static findings

### 1. DRP deadlock timeouts are accounted nowhere

**Severity:** high
**Where:** `core/nrda_fleet/agent.py:1269`, `core/nrda_fleet/metrics.py:216-224`.
**Defect:** the agent publishes `drp_done` with `detail="timeout"` at every rung expiry; the ledger pops the epoch but only counts `resolved` when `detail != "timeout"`, and only `drp_escalated` (rung > 3) sets `status="needs_you"`. A deadlock timing out at rungs 1-3 is therefore counted as a new `deadlocks` plan each rung, never resolved, never escalated, and its incident stays open.
**Evidence:** `~/.nrda/runs/20261015-095812.json` shows `deadlocks=1, resolved=0, escalated=0, incidents_open=1`. Consequence: the "0 unhandled deadlocks (`needs_you` = 0)" claim in README and FINAL_AUDIT cannot fail.
**Repro:** inspect the run file above, or let any deadlock expire at rung 1-3 and read the ledger.

### 2. The benchmark harness reports success when runs crash (LATENT - see correction B4)

**Severity:** high
**Where:** `benchmarks/run_scenarios.py:127-128`.
**Defect:** every per-run exception is caught, printed as `FAILED`, and `main()` still exits 0; `nrda.sh bench` then runs `report.py`, which aggregates whatever raw files exist.
**Evidence:** `--quick` means S1+S2 x 2 seeds = 4 runs, but `benchmarks/results/raw/` held exactly one file (`S1_nominal__s1.json`) from 13 Oct, and `summary.md` was published anyway, labelled "1 seed(s)" with S2 silently absent.
**Repro:** run `./nrda.sh bench` with a scenario that raises; the exit code is 0 and a summary is still written.

### 3. `run_id` never reaches the safety monitor

**Severity:** high
**Where:** `ros2_ws/src/nrda_fleet_ros/nrda_fleet_ros/safety_monitor_node.py:40`, `launch/fleet.launch.py:57-58`, `gateway_node.py:63`.
**Defect:** the monitor's `run_id` defaults to `""` and the launch file passes only `robots` and `on_collision`, while the gateway independently defaults to a `strftime` stamp.
**Evidence:** all 143 rows of the pre-existing `~/.nrda/events.db` had `run=''`, and event ids collide across runs (`E00001` appeared 19 times). Consequence: safety events cannot be joined to a run's KPIs, and `POST /api/safety/events/{id}/ack` plus the console row lookup are ambiguous.
**Repro:** `sqlite3 ~/.nrda/events.db "select run, count(*) from events group by run"`.

### Runtime findings

#### R1. The DRP yielder is elected from outside the wait-for cycle

**Severity: high. Root cause of the liveness failure.**

`deadlock_group` (`core/nrda_fleet/deadlock.py:119-134`) merges cycle members with any stalled
robot within 3 m. `make_plan` then elects the robot that must give way purely by precedence over
that merged group - `max(movable or group, key=lambda m: m.key)` at `deadlock.py:290`, `:298`,
`:308`, `:330`, and `max(opposing or candidates or [prio], ...)` at `:323`, where
`Member.key = (-priority, id_key(rid))` (`:60-62`).

For the group `{AMR_2, AMR_5, AMR_7, AMR_17}` at equal priority that elects **AMR_17**, the
proximity-merged robot with no wait-for edges, while AMR_7 - the robot the cycle actually needs
to yield - was issued `hold` on all three rungs and moved 0.00 m. A robot outside the cycle
cannot break the cycle, so the protocol exhausts its rungs by construction. `Member` already
carries `waiting_for` (`deadlock.py:56`), so the topology needed to elect correctly is present
and unused.

Escalation is also not terminal in a useful sense: rung 4 publishes `drp_escalated`, tears down
the frozen zone and precedence token, commands no robot, pops `_drp_rung`, and sets a 60 s
cooldown - after which `rung` reads back as 1 and the identical sequence replays. That is a
~120 s escalate/cooldown lap, which is why `deadlocks_escalated` reached 16 while
`deadlocks_resolved` stayed at 8: the counter measures laps, not distinct faults.

#### R2. A blocked robot can be invisible to the deadlock detector

**Severity: high.**

`waiting_for` is written in exactly one place, `_handle_waits` (`core/nrda_fleet/agent.py:1038-1041`),
and derives solely from `plan.blocked_by`. Several paths reach v=0 in a driving mode with no
edge published; three were material here:

- **Station queue cut.** `_queue_legs` returns `[]` - *"no legal spot between here and the
  doorway: hold where the robot is"* (`agent.py:971`) - and `_legs_to_plan` (`:838-877`)
  truncates the route when the goal station is occupied. With an empty leg list `_authority`
  returns `(0.0, ())` (`core/nrda_fleet/scheduler.py:384`): zero waits, zero `auth_blockers`,
  so `waiting_for` is cleared even though the occupying peer is known by rid inside
  `_station_taken`. Unbounded - it holds until the occupant leaves.
- **Dead DRP fallback.** `agent.py:1040-1041` is meant to make a DRP-held robot advertise that
  it waits for the priority robot, but `_drp_prio_rid` is never assigned a non-empty value
  anywhere in the tree (only `:164` `= ""`, reads at `:1040`, `:1041`, `:1188`, `:1189`, and
  `:1191` `= ""`). A held robot therefore always publishes `waiting_for = []`.
- **Hold expires mid-rung.** `_drp_hold_until = self.t + 10.0` (`agent.py:1306`) against
  `RUNG_S = 20.0`: the hold lapses half-way through the rung, the held robot re-plans, and
  `set_route_claims` re-books the same cell *preserving the original claim stamp*
  (`core/nrda_fleet/claims.py:255-271`), regaining precedence over the priority robot before the
  coordinator judges the rung.

Consequence: `metrics.risk()` and DRP cycle detection both build their graph from `waiting_for`,
so these robots are invisible to the console hazard view and reachable by DRP only through the
crude 3 m proximity merge - which then elects one of them, per R1.

the run:

| `drop_1` | 6 |

#### R4. `utilisation_pct` counts motionless robots as utilised

**Severity: medium (metric correctness).**

`busy` is defined by mode alone, with no speed term (`core/nrda_fleet/metrics.py:24`:
`mode in ("to_pickup","loading","to_drop","unloading")`). The run reported **89.3 % utilisation
with 15 of 20 robots at a dead stop**, because a gridlocked robot never returns to `parked`. A
jammed fleet therefore scores *higher* utilisation than a working one, and the `utilisation_pct
> 70` threshold cannot detect a gridlock.

#### R5. `throughput_per_hour` cannot detect a gridlock either

**Severity: low (metric correctness).**

It is computed over completed tasks against elapsed time, with no reference to offered load. The
run "passed" `throughput_per_hour > 120` at t=562 while 73 % of released tasks had never been
assigned, and only fell below the threshold later. Completion rate (13.8 %, then 11.2 %) and
queue depth (106 tasks) are the honest signals.

#### R6. Real-time factor is below the documented figure

**Severity: low.**

`FINAL_AUDIT` states ~1.0x real time headless. Measured: **0.889** (561.8 s of simulation in
631.9 s of wall time) with `gui:=false rviz:=false`, on 12 cores with nothing else running.

### What the run confirms and refutes

Confirmed by live evidence:

- Static finding 1 (DRP timeout accounting): counters read `deadlocks=48, resolved=8,
  escalated=10` at t=562, i.e. **30 of 48 plans accounted nowhere**.
- Static finding 3 (`run_id`): `select distinct run from events` returned `('')` for this run.

Refuted:

- README: "**0 unhandled deadlocks** (`needs_you` operator alerts = 0); all transient
  contentions resolved autonomously via DRP" - 16 escalations and two incidents left
  `needs_you` for over 280 s.
- `FINAL_AUDIT` threshold `deadlocks_escalated == 0` - failed.
- `SAFETY_CASE`: no `incidents[].status == "needs_you"` under `scenario:=busy` - failed on that
  exact scenario.
- README: peak 251.2 / sustained 225.6 tasks/h at 84.4 % utilisation - measured peak 204.8,
  ending at 100.1.

Upheld:

- Zero robot-robot, robot-static and obstacle collisions, and zero near misses, across 940 s at
  peak density with 20 robots. The emergency layer, lidar safety stop and claim system did their
  job throughout; the failure is entirely one of liveness, not proximity. This is also the
  argument against reducing `min_gap`: the margins were never the constraint.

### Deliberately not changed in this pass

So that F1-F4 can be measured in isolation:

- `_handle_waits`' `abs(self.v) < 0.05` velocity gate and the `plan.waits[0].t_start <= t + 1.0`
  time gate (`agent.py:1038-1039`), both of which can clear a legitimate edge.
- The DRP `pass` action, which only zeroes `_drp_hold_until` (`agent.py:1323-1324`) and never
  makes the priority robot re-plan or clear its `forbid` entries.
- Single-coordinator election: `epoch = f"{coordinator}:{int(t*10)}"` plus per-robot
  `_drp_detect`/`group` means two members can publish competing plans. The module docstring
  promises a lowest-AMR election that the code does not implement.
- DRP state keyed on `frozenset(plan.members)` when written but `frozenset(group)` when read
  (`agent.py:1225-1234` vs `:1268-1282`), while `plan.members` is mutated by chain pulls
  (`deadlock.py:336`) - can strand the rung counter or lose the cooldown.
- The 1.5 m displacement success test in `_drp_supervise` (`agent.py:1255-1256`), which judges
  resolution by how far the priority robot moved rather than by whether the cycle is gone.
- `utilisation_pct` (R4) and `throughput_per_hour` (R5), both of which need a speed term and an
  offered-load reference respectively.
- The lidar emulator's 12 m `range_max` (finding 7), the gateway's unauthenticated `0.0.0.0`

### B1. The 2-D benchmark cannot observe the failure mode that dominates Gazebo

**Severity: high (methodological).** `S3_busy` in the 2-D simulator reports 288.0 tasks/h with
**32 deadlocks resolved**; the same `busy` scenario in Gazebo collapsed to 100.1 tasks/h with 16
escalations and `deadlocks_resolved` frozen at 8. Two reasons:

1. `run_scenarios.py` records only `deadlocks_resolved` - never `deadlocks` (attempts) or
   `deadlocks_escalated`. A run in which DRP fails completely is numerically indistinguishable
   from one in which it succeeds, and `report.py`'s `METRICS` table has no column for it.
2. `Sim2D` defaults to `latency=0.0` while Gazebo applies ~0.1 s actuation latency, and the 2-D
   model has no wheel physics. `FINAL_AUDIT:402` itself lists latency-induced problems as a
   known Gazebo fragility, so the harness cited for reproducibility omits the effect that breaks
   the system.

Since README and `FINAL_AUDIT` point at this benchmark as the evidence for the fleet's headline
numbers, this is the most likely reason the gridlock was never caught.

### B2. Achieved bumper gaps are far below the configured minimum

**Severity: medium.** `min_gap_m` reached **0.025 m** in S2 and 0.033 m in S3, against
`EmergencyConfig.min_gap = 0.15 m` and the monitor's `near_gap = 0.10 m`. Only 3 and 2 near
misses were flagged respectively, because `SafetyTruth.check` requires a closing speed
`rel > 0.05` and de-duplicates per pair over 2 s. So the near-miss counter substantially
under-reports how close the fleet actually comes, and there is no clearance headroom to reclaim
by lowering `min_gap`.

### B3. Near-continuous replanning

**Severity: medium.** 37,532-40,238 replans per run. Twenty robots over 600 s at the documented
4 Hz planning budget is 48,000 opportunities, so robots replan on 75-83 % of ticks. That does
not match the "adaptive compute (4 Hz while driving, 1 Hz while parked)" description and
warrants its own investigation.

### B4. Correction to static finding 2

Static finding 2 claimed the harness had silently swallowed three failed runs on 13 October,
inferred from only one raw file being present. Re-run fresh, **all three scenarios passed**. The
code defect is real and unchanged - `run_scenarios.py:127-128` catches every per-run exception,
prints `FAILED`, and `main()` still exits 0, after which `report.py` publishes from whatever raw
files exist - but it is **latent**: there is no evidence it has fired. The earlier run was most
likely interrupted or invoked with narrower arguments. Finding 2 is downgraded accordingly.
